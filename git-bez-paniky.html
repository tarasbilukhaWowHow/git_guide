01

Що таке Git

Git — це система контролю версій. Але простіше сказати так: це система, яка запамʼятовує те, що ви зробили в папці, і дозволяє ефективно працювати в команді.

У нас є репозиторій — основна папка з файлами проєкту. Ви вносите туди свої зміни й доповнюєте проєкт.

Що означає «внести зміни»?

Це означає зробити свою версію проєкту. Наприклад, у нас є файл:

Hello World!

Ви дописуєте в нього рядок:

Hello World!
And people

Це і є зміни. Щоб їх зафіксувати, потрібно їх закріпити — у Git ми робимо це командою git commit. Ця команда фіксує зміни і створює вашу версію проєкту.

Коміт — це не збереження файлу. Файл ви зберігаєте редактором. Коміт — це відмітка «ось цей стан проєкту я вважаю завершеним кроком». До неї завжди можна повернутись.
02

Git і GitHub — це різні речі

Щоб зрозуміти різницю, треба зрозуміти різницю між локальним і віддаленим репозиторієм.

Уявіть, що ви зафіксували зміни через git commit. Тепер ваша версія лежить на компʼютері — локально. Але є ще сайт GitHub, і якось треба зробити так, щоб версія з вашого компʼютера потрапила туди.

  • git push — закидає вашу локальну версію зі змінами в спільну папку, де працюють усі.
  • git pull — робить протилежне: якщо колега закинув файл на GitHub і ви хочете, щоб цей файл був у вас на компʼютері, ви робите git pull.
Git — це програма на вашому компʼютері, вона працює навіть без інтернету. GitHub — це сайт, де лежить спільна копія. Git може жити без GitHub, GitHub без Git — ні.
03

Гілки: як не зламати робочу версію

Уявіть проєкт як зошит. Є чистовик — він завжди має бути охайним, бо його читають усі. Це гілка main.

Але вам треба спробувати щось нове, і ви не впевнені, що вийде. Логічно не писати одразу в чистовик — ви берете копію сторінки і пишете на ній. Це і є гілка (branch).

Гілка — просто окрема лінія коммітів. Ви створюєте її від поточного стану проєкту, робите там свої комміти, і main при цьому не змінюється. Коли все готово — зливаєте гілку назад у main командою git merge.

Навіщо це все? Поки ви колупаєтесь у своїй гілці, колега спокійно працює в main, і ви одне одному не заважаєте. А якщо ваша ідея не спрацювала — гілку просто видаляють, і в проєкті не лишається жодного сліду.
04

Чому виникає мердж-конфлікт

Коли ви робите git merge (або git pull, бо всередині нього теж є merge), Git намагається скласти дві версії файлу в одну. І здебільшого він робить це сам, ви навіть не помічаєте.

Git дивиться, які рядки змінила кожна сторона. Ви правили початок файлу, колега — кінець? Git спокійно бере обидві правки. Проблема починається, коли ви обоє змінили один і той самий рядок по-різному.

Тут Git зупиняється. Він не вгадує, чия версія правильна — бо звідки йому знати. Він каже: «розберіться самі» і лишає обидва варіанти прямо у файлі.

Коротко: конфлікт — це не поломка і не ваша помилка. Це запитання від Git: «дві різні правки одного рядка, яку лишаємо?»

Спробуйте самі

Ви у гілці feature дописали And people. Колега тим часом у main змінив той самий другий рядок на And cats. Ви робите merge:

feature — ваша гілка
Hello World! And people
main — гілка колеги
Hello World! And cats 
$ git merge feature
CONFLICT (content): Merge conflict in hello.txt
Automatic merge failed; fix conflicts and then commit the result.

Відкриваємо hello.txt — Git поклав туди обидва варіанти і позначив їх маркерами:

<<<<<<< HEAD
Hello World!
And cats          ← те, що вже є у вашій поточній гілці
=======
Hello World!
And people        ← те, що приходить з гілки feature
>>>>>>> feature

Розвʼязати конфлікт = відредагувати файл руками так, як він має виглядати. Що залишаємо?


          
Маркерів <<<<<<<, ======= і >>>>>>> у файлі більше немає — значить, можна фіксувати:

          
$ git add hello.txt
$ git commit -m "merge feature"
[main 7f3a91c] merge feature

          
Готово. Правильної відповіді тут не існує — правильна та, яку ви обрали свідомо. Саме тому Git і питає вас, а не вирішує сам.

Все пішло не так? git merge --abort скасовує злиття і повертає все як було до merge. Це безпечна кнопка «вихід».


    
Як рідше ловити конфлікти

    
    
      
  • Робіть git pull частіше. Що довше ваша гілка живе окремо, то більше розходження.
    • 
      
  • Маленькі комміти й короткі гілки. Гілка на два дні конфліктує рідше, ніж гілка на два місяці.
    • 
      
  • Домовляйтесь у команді, хто який файл зараз чіпає. Найдешевший спосіб.
